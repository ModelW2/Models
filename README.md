# Галерея 3D-визуализаций + FBX-вьюер

Статический сайт: галерея рендеров и превью моделей, по клику модель
открывается в 3D-вьюере на three.js. Ни сборки, ни Node.js — только
статические файлы, поэтому его можно положить на GitHub Pages как есть.

## Структура

| Файл / папка | Что это |
|---|---|
| `index.html` | галерея: карточки моделей и рендеров |
| `viewer.html` | 3D-вьюер, открывается как `viewer.html?model=Butovo.fbx` |
| `*.fbx`, `*.png`, `*.jpg` | исходники в корне: модель и одноимённый скриншот |
| `thumbs/`, `large/` | пережатые превью, **создаются скриптом** |
| `site-data.js` | список моделей и рендеров, **создаётся скриптом** |
| `build-site.ps1` | сканирует корень, делает превью, пишет манифест, чистит лишнее |
| `make-upload.ps1` | собирает `C:\WV-upload` — плоский комплект для ручной загрузки |
| `serve.ps1` | локальный веб-сервер на чистом PowerShell |

## Как добавить работу

1. Положить в корень проекта файл `Имя.fbx` и одноимённый скриншот `Имя.png`.
   Точное совпадение имён необязательно: `KuvekinoLite.fbx` подхватит
   `Kuvekino.png` по общему префиксу. Скриншот без модели просто попадёт
   в раздел «Рендеры».
2. Пересобрать превью и список:

```bash
powershell -ExecutionPolicy Bypass -File C:\WV\build-site.ps1
```

Исходники весят до 15 МБ штука — в галерею они не отдаются. Скрипт кладёт
рядом сжатые JPEG: `thumbs/` (1000 px) для карточек и `large/` (2200 px)
для полноэкранного просмотра. На текущем наборе это 3.4 МБ вместо ~90 МБ.

Превью от удалённых или переименованных исходников скрипт убирает сам —
иначе они копились бы в папке и уезжали в репозиторий.

В галерее: клик по модели открывает её в 3D, клик по рендеру — полный
экран с перелистыванием (стрелки по бокам, клавиши ←/→, свайп на телефоне,
Esc — закрыть).

## Запуск локально

```bash
powershell -ExecutionPolicy Bypass -File C:\WV\serve.ps1
```

Дальше `http://localhost:8080/`.

**Сервер нужен обязательно.** Если открыть `index.html` двойным кликом,
галерея нарисуется, но 3D работать не будет: модели грузятся через `fetch`,
а из `file://` браузер запрещает читать локальные файлы. Проявляется это
как «нажимаю Открыть в 3D, а показывается демо-сцена с кубиком».
Вьюер в таком случае показывает поверх сцены сообщение с объяснением —
галерею предупреждением не засоряем.

На GitHub Pages ограничение не действует — там уже http.

## Публикация на GitHub Pages

Сайт полностью статический, так что достаточно закоммитить папку и включить
Pages в настройках репозитория (Settings → Pages → ветка `main`, корень `/`).
Все пути относительные, поэтому работает и в подпапке вида
`username.github.io/repo/`. В корне лежит пустой `.nojekyll` — иначе Jekyll
на стороне GitHub может выкинуть часть файлов.

### Что попадает в репозиторий

Коммитить нужно: `index.html`, `viewer.html`, `site-data.js`, папки
`thumbs/` и `large/`, файлы `*.fbx`, `.nojekyll` и скрипты.

Исходные highres-скриншоты в репозиторий **не попадают** — см. `.gitignore`.
Это входные данные для сборки: сайту они не нужны, а весят под 70 МБ.
Галерея живёт на пережатых `thumbs/` и `large/` (около 3.5 МБ на всё).

### Ограничения, о которые легко споткнуться

- **Загрузка через сайт GitHub (drag-and-drop) обрезает файлы на 25 МБ.**
  Модели по 20–45 МБ так просто не зальются: часть молча не уедет. Нужен
  `git push` из командной строки.
- Через git лимит — **100 МБ на файл**, предупреждение с 50 МБ. Модели
  по 20 МБ проходят спокойно, но файл под 50 МБ лучше сразу класть в Git LFS.
- У Pages мягкий лимит 1 ГБ и 100 ГБ трафика в месяц. При модели в 20 МБ
  это примерно 5000 просмотров.
- Если моделей станет много, их стоит конвертировать в glTF + Draco:
  весит в разы меньше FBX и грузится быстрее.

### Вариант 1 — через git (надёжно)

```bash
cd C:\WV
git init -b main
git add -A
git commit -m "Галерея 3D-визуализаций"
git remote add origin https://github.com/USER/REPO.git
git push -u origin main
```

### Вариант 2 — руками через сайт GitHub

У веб-загрузчика две особенности, на которых легко потерять половину сайта:
он **не читает `.gitignore`** (утащит исходники фото) и **не умеет папки**
через кнопку «choose your files» — каталоги можно только перетаскивать, и
это срабатывает не всегда.

Поэтому есть отдельный шаг, который раскладывает всё плоско — ни одной
вложенной папки:

```bash
powershell -ExecutionPolicy Bypass -File C:\WV\make-upload.ps1
```

Получается `C:\WV-upload`: превью переезжают из папок в корень как
`t_Имя.jpg` (карточка) и `f_Имя.jpg` (полный экран), пути в `site-data.js`
переписываются автоматически. Дальше папку можно выделить целиком и
перетащить на страницу загрузки.

Модели заливать отдельными коммитами: 47 МБ одним куском браузер часто
не дотягивает, и файлы молча пропадают.

Пустые папки (например `assets`) git не хранит в принципе — он отслеживает
файлы, а не каталоги. Если папка нужна на сервере, в неё кладут файл-заглушку.

Дальше Settings → Pages → Source: ветка `main`, папка `/ (root)`.

## Что реализовано

- **Небо + солнце**: процедурное небо (`Sky.js`, модель Прейетама) с
  управляемым положением солнца. От неба строится IBL-окружение (PMREM) —
  естественный skylight и отражения, как Sky Atmosphere + Sky Light в Unreal.
- **Мягкие тени — PCSS**: собственная реализация поверх шейдерного чанка
  three.js. Сначала ищутся «блокеры» (что заслоняет солнце), по средней
  дистанции до них считается ширина полутени, и уже с этим радиусом делается
  PCF. Чем дальше объект от поверхности, тем мягче его тень — как в жизни.
  Ширина полутени берётся физически, через угловой размер солнца (реальный
  ≈ 0.53°, в GUI регулируется).
- **Объёмный свет**: марш по лучу взгляда от камеры до поверхности; на
  каждом шаге shadow map солнца отвечает, освещена эта точка воздуха или
  она в тени здания. Даёт дымку и рассеяние вперёд. Самый дорогой из
  оставшихся проходов, **по умолчанию выключен**.
- **Ambient Occlusion**: экранный проход по буферам глубины и нормалей —
  контактное затемнение в стыках и впадинах.
- **PBR-материалы**: материалы FBX (Phong) конвертируются в
  `MeshStandardMaterial`, ACES Filmic / AgX / Neutral tonemapping на выбор,
  корректные цветовые пространства, анизотропная фильтрация всех карт.
- **Встроенные (packed) PBR-текстуры**: штатный `FBXLoader` умеет
  подключать только классические Phong-свойства — metalness/roughness в
  модели материалов FBX просто нет. Вьюер сам разбирает бинарную структуру
  FBX, находит Video/Texture/Material и связи между ними, и подставляет
  `metalnessMap`/`roughnessMap` по именам текстур (суффиксы `_d/_m/_r/_o`).
- **Масштаб сцены**: туман, дистанции орбиты камеры, размер пола и смещения
  теней пересчитываются от габаритов загруженной модели. FBX почти всегда
  в сантиметрах, и константы, подобранные под сцену в 3 единицы, на модели
  в 600 единиц не работают.
- **Скриншот**: кнопка рендерит кадр в 1920×1080 и сохраняет PNG.

## Исправленные проблемы (эта итерация)

Модель выглядела «сплошной белой», а дома не отбрасывали тень на землю.
Причин было три, все найдены и подтверждены замерами:

1. **Потеря `emissiveIntensity` при конверсии материалов.** В FBX цвет и
   сила свечения — разные свойства (`EmissiveColor` и `EmissiveFactor`).
   Экспортёр записал `EmissiveColor = white` при `EmissiveFactor = 0`, то
   есть «свечения нет». Конвертер переносил только цвет, и
   `emissiveIntensity` у нового материала оставалась дефолтной единицей.
   Земля, `GroundEl` и часть корпусов начинали светиться чистым белым:
   отсюда и «слишком белый» вид, и полное отсутствие теней — свечение
   добавляется после расчёта освещения, и затенить его невозможно.
2. **Принудительная инверсия roughness.** Канал `_r` в этом файле — обычная
   roughness (карта почти белая, поверхность шершавая). Инверсия делала из
   всех стен зеркала, отражающие яркое небо. Теперь по умолчанию выключена
   (галочка в GUI осталась — для пайплайнов, где `_r` реально хранит
   glossiness).
3. **VSM-тени на большой сцене.** VSM хранит моменты глубины в half-float;
   на сцене глубиной в сотни метров точности не хватало, начинался light
   bleeding, и тень пропадала целиком. Заменено на PCSS; фрустум тени
   прижат к границам сцены, смещения от acne масштабируются размером
   текселя в мировых единицах.

Дополнительно:

- Клетчатый пол вьюера **автоматически прячется**, если у модели есть своя
  земля (широкий плоский меш у основания) — раньше он спорил с ней по
  глубине и торчал из-под модели другой яркостью. Если своей земли нет,
  пол остаётся: иначе отдельно стоящему объекту не на что отбрасывать тень.
- **Баланс солнце/небо.** Замер по кадру показал, что небо давало даже
  больше света, чем солнце (0.73:1) — картинка расплывалась в дымку, тени
  еле читались. Выставлено ~4:1, как в ясный день.
- **Сглаживание**: `EffectComposer` по умолчанию рендерит в обычный таргет,
  и antialias из конструктора рендерера в постобработке не работал —
  включён multisample-таргет.
- **Анизотропная фильтрация** для всех карт: без неё крыши и асфальт под
  острым углом шли муаром.

## Управление

- ЛКМ — вращение, ПКМ — панорама, колесо — зум.
- Зум идёт **к точке под курсором** и не имеет практического нижнего упора:
  можно подъехать вплотную к любой детали. Ближняя плоскость отсечения
  подстраивается под текущее расстояние до цели, иначе на модели в сотни
  единиц геометрия срезалась бы задолго до сближения.
- Модели открываются только из галереи (параметром `?model=`), кнопок
  загрузки FBX во вьюере нет. Панораму `.exr`/`.hdr` можно бросить в окно
  или открыть кнопкой «HDRI».
- Правая панель: небо и солнце (высота/азимут/яркость солнца/яркость неба/
  свет от неба/экспозиция/tonemapping), объёмный свет, качество и производительность,`r`n  HDRI-окружение, тени (PCSS, угловой размер солнца, разрешение карты), AO,
  override материалов, сцена (пол, туман, авто-вращение).

## Известные особенности этого семейства FBX

- **`_o` — это Opacity, не AO.** `FBXLoader` подключает её как `alphaMap`
  через legacy-свойство `TransparencyFactor`. Такие материалы переведены на
  `alphaTest`-вырезание вместо alpha-blending, иначе решётки и перфорация
  рендерились сплошными пятнами.
- **Roughness из Phong `shininess`** — приближение. У экспортёра shininess
  почти всегда дефолтный (25 у 3ds Max), буквальный пересчёт даёт ~0.27, и
  бетон превращается в полированный камень. Нижняя граница поднята до 0.35;
  стекло (высокий shininess + прозрачность) остаётся глянцевым.

## Производительность

Вьюер упирался в 4 FPS на слабой видеокарте. Замер на сцене в 531 тыс.
треугольников показал, что решает не какой-то один эффект, а **разрешение
рендера**:

| что меняли | мс на кадр |
|---|---|
| 1920×1080 | 34 |
| 1280×720 | 18 |
| 960×540 | 12 |
| выключить AO (1080p) | −3 |
| выключить сглаживание (1080p) | −5 |

Раньше pixel ratio был жёстко `min(devicePixelRatio, 2)`: на ноутбуке
с ретиной кадр 1080p считался в 3840×2160 — вчетверо дороже. Это и давало
те самые 4 FPS.

Теперь есть три уровня качества (раздел «Качество и производительность»).
Уровень меняет разрешение рендера, сглаживание, размер карты теней, число
выборок PCSS и ambient occlusion. По умолчанию стоит «Авто»: старт со
среднего, и если частота держится ниже 24 FPS полторы секунды — уровень
понижается сам. Только понижается: авто-повышение давало бы качели на
границе. Поднять можно вручную.

Убрано ради скорости: объёмные облака, тень от них и экранные лучи солнца.
Объёмный свет оставлен, но выключен по умолчанию.

Ещё две правки, заметные на слабых машинах:

- Карта теней перерисовывается **по событию** (загрузка модели, поворот
  солнца), а не каждый кадр. На тестовой машине выигрыш утонул в шуме —
  там узкое место не в этом; на слабой видеокарте экономия должна быть
  заметнее, потому что в карту рендерится вся геометрия целиком.
- Проход нормалей рисует сцену второй раз и нужен только для AO и
  объёмного света. Если оба выключены — пропускается целиком.

## Возможные доработки

- Bloom/vignette для более «киношной» картинки.
- Каскадные тени (CSM) — если понадобится качество теней и вблизи, и на
  всю площадку одновременно.
- Упрощение геометрии (LOD) — при 500 тыс. треугольников это следующий
  по величине рычаг после разрешения.
